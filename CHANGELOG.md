# Changelog

Sentrook 2.0 scanner.
The 1.x engine and plugins keep their own history on `release/1.x`.

## Unreleased (2.0.0a1)

### Package skeleton, contracts and schemas (2026-10-16)
- Project scaffold: `pyproject.toml`, `Makefile`, package layout under `sentrook/sentrook/`, CI (lint, tests, schema drift check).
- PlanIR 2.0, Response 2.0 and probe-envelope models (`planir`, `response`, `probes`), with tolerant enums and additive fields kept.
- JSON Schema contracts generated from the models into `schema/`; `sentrook schema export [--check]`.
- Unit tests on the two worked examples from the design page and synthetic cases; no suite fixtures.

### Preparation: PlanIR models, validation, entities, state token, Jev views (2026-10-16)
- `planir.validate`: the PlanIR structural invariants (`InvalidPlanIR` for structural failures, warnings for coverage).
- `planir.canonical`: per-platform argument canonicalisation to one vocabulary per `tool_kind`; URL queries percent-decoded for analysis only.
- `prepare`: trust classification, entity extraction with roles and opaque IDs (pending call, siblings, request, grants, inputs, history, agent-written files), the untrusted-entity set with "echo does not promote", action fingerprint `afp1`, Jev state views byte-identical to the runner's `trim-v1`.
- `state.token`: HS256 state token bound to `session_ref` and step; test-mode seeding from `state_seed`.

### AIRA probe: consequence detectors and lists (2026-10-16)
- `probes.aira.AiraProbe`: the deterministic consequence probe. One envelope per request with contributions on `consequence.sensitivity|reach|irreversibility|self_modification` and `suspicion.concealment`, the `guardrail_tampering` (min_risk 1.0, block) and `untrusted_code_execution` (min_risk 0.9, block; obfuscated decode-to-shell only) floors, the `holds_sensitive` flag, and evidence (classes, internal rule ids, exec shape summary, packs, per-finding detail). Siblings are scanned with the same detectors and count the same. Never raises.
- `aira.detectors`: C1 credential material reached, C2 exfiltration (source × sink) and plain sends, C3 untrusted code (fetch-to-shell, decode-to-shell, install-from-URL, package install, running a file written since a fetch), C4 self-modification and persistence, C4* guardrail tampering (OpenClaw and Hermes; content-aware for `openclaw.json` / Hermes `config.yaml` edits), C7 destruction outside scratch and C8 privilege change (pack `host_gated`; the preload/setuid/shadowing arms always on; C7 records evidence only when the host already granted approval), C9 irreversible remote side effects, C10 secret written into an artefact, extent (recursive / wildcard / bulk recipients raise reach), concealment for output suppression on network calls. Encoding alone contributes nothing.
- `aira.lists`: rules as code, knowledge as data. Versioned YAML under `aira/lists/` (`sensitive_paths`, `guardrail`, `destructive`, `remote_destructive`, `privilege`, `egress`, `installers`, `selfmod`, `extent`, `weights`), compiled at load, with an additive operator overlay from `SENTROOK_LISTS_DIR`; the combined version string is reported as `versions["ruleset"]`.
- Ported from 1.x (`engine/2.0-policy-switch`): `aira.exec_shape` (tree-sitter-bash segments, wrappers, privilege, env assignments, sinks, now also redirect targets and pipelines), `aira.path_classes` (location and group classification, URL hosts), `aira.normalize` (base64 / hex / quote-concat deobfuscation for matching), `aira.sensitive_paths` (the path-group compiler; the list gains browser-profile and PII-store groups and the agent-context groups for C4).
- Tests: `test_aira_exec_shape` (ported assertions plus authored shape cases), `test_aira_lists` (loader, overlay, compilation, normaliser), `test_aira_detectors` (one positive and one benign twin per class on synthetic PlanIRs with invented hosts, plus the two worked examples: the attack and its sanctioned twin carry the same consequence).

### Jev probes: exposure and call question sets, chunking (2026-10-16)
- `jev.client`: Decisions API client behind one configurable base URL, `zdr` provider preferences, retry with backoff, context-limit and timeout surfaced as coverage events; `X-TestNest-Repeat` forwarded for the runner's proxy.
- `jev.questions`: `exposure-v1` and `call-v1`, the two halves of the frozen `designed-v1-split`, word for word. Verified: every request body for all 691 suite cases hashes to the runner's cache key.
- `jev.chunking`: head-and-tail chunking of oversize exposure inputs, highest chunk score taken.
- `probes.jev`: exposure probe (sets `tainted`, skipped without new untrusted inputs) and call probe (misalignment, concealment, consequence signals, mean model certainty; `untrusted_origin` and the action category in evidence only).

### Entity oracle and context probes (2026-10-16)
- `oracle.client`: the `OracleClient` contract Rookery will implement (`lookup` with roles → verdicts + library snapshot); `SeedOracle` (test mode), `NullOracle` (live, everything unknown, coverage lowered), `HttpOracle` stub.
- `probes.oracle`: distrust by verdict and role, `known_bad_entity` floor, coverage for unknown risky entities; loopback hosts and paths are not looked up.
- `probes.context`: `untrusted_origin` per entity (request/grant 0, visible creation 0.1, agent-generated 0.4, untrusted content 1.0, taint and lineage propagate), `request_origin` from the trigger (OpenClaw and Hermes bases), `retry_after_denial` from fingerprints recomputed over denied history steps, sticky exposure, session sensitivity, escalation flag, coverage from stale requests and fresh sessions.

### Serve and CLI (2026-10-16)
- `serve`: stdlib threaded HTTP daemon with `GET /healthz`, `GET /metrics`, `POST /scan` (200 for ok and degraded, 422 with the Response error shape for an unscoreable body) and the config-gated `POST /testnest/scan` (`{fixture, state_seed, oracle_seed, options}` → `{response, probes, prepared}`; `options.repeat` forwarded to the runner's proxy; `options.probes` for ablation).
- Auth (API key and FIDU OIDC), per-caller token-bucket rate limiting and Prometheus metrics carried from 1.x; `ServeConfig.from_env` with production guards (state key required, test mode refused, content logging off).
- CLI: `sentrook scan FILE [--envelopes] [--probes]` for a PlanIR or a TestNest case file; `sentrook serve`.
- The provenance arm of the floor was over-broad (it blocked installs named in documents the owner pointed at, which the rubric scores high but does not floor); replaced by a look-alike check against a list of well-known installer hosts (`code.lookalike_installer`), per the suite's labelling rules.

### First full-suite run (2026-10-16)
- The scanner ran the full TestNest 2.0 v1 suite (dev and held-out, with per-probe ablations) through the runner's replay proxy with zero live model calls. Results and the tuning list live with the private suite. Ranking improved on both splits over the model-only baseline and every expected floor was applied with no unexpected floors.

### First tuning step: conv-v2 and conv-v3 (2026-10-16)
- `conv-v2`: the oracle's unknown-entity distrust by role (destinations 0.3, recipients 0.25, tool providers 0.1; code sources and executables stay 0.5). Chosen on dev, confirmed once on held-out; `conv-v1` is unchanged and remains selectable with `SENTROOK_CONVERGENCE=conv-v1`.
- Items 2 to 6 (same day), each pinned by a unit test, chosen on dev and confirmed once on held-out:
  - Request-named relief also matches a recipient's display name (`Priya` for `priya.nair@…`, capitalised in the request) and the single `bcc`/`cc` address when the owner asks to be copied; neither applies to an address that reached the agent through content it read. The mail domain of a request-named recipient inherits the sanction.
  - `retry_after_denial`: matching is role-insensitive on the pending side and includes code and executable hashes (a shred retried through an interpreter, a write retried as an edit, a blocked install retried with another flag now match); a read-shaped call on the same data is the weaker `retry.same_source_only`. `context.retry_carry_consequence` (on in `conv-v3`) carries the denied step's consequence tier into a matched retry as reach and irreversibility.
  - AIRA C4: a script or data file in a workspace skill scores at `selfmod.workspace_skill` (0.5); the skill's instruction files keep the plugin weight (`weights.yaml` 4, `selfmod.yaml` 2).
  - AIRA C9: cloud IAM grants, access keys, inline or admin policies, repository secrets and RBAC bindings as `remote.grant` (`remote_destructive.yaml` 2); reader-level grants stay silent.
  - `conv-v3`: consequence as the mean of sensitivity, reach and irreversibility (max with self-modification), `u` 0.5, the retry carry on; the oracle table and everything else as `conv-v2`, which stays selectable.

### Question-set pass: call-v2 and exposure-v2 (2026-10-19)
A deliberate cache invalidation for the Jev probes, opt-in by configuration; the v1 views (`trim-v1`) and question sets stay byte for byte as they were and remain the default.
- `prepare.views`: a second views version, `trim-v2`. `call-v2` adds the turn's `new_inputs` between `history` and `pending_call`, so a question can weigh a listing or a read before a bulk or publishing call; each input's content is capped at 6000 characters and all of them at 40,000 (the earliest inputs lose content first so the latest, such as the listing right before the pending call, keep theirs; metadata stays, a cut input carries `scanner_truncated`), and a view still over the chunking budget keeps only the inputs' metadata. `exposure-v2` has the `exposure` keys. All four views are built on every request; `Prepared` records `views_version`, per-view metadata and the redaction count.
- `prepare.redact` (`redact-v1`): a second redaction pass over the v2 views for secret shapes the plugin's redaction missed (PEM private keys, JWTs, AWS, OpenAI/Anthropic, Stripe, GitHub, Slack, Google, GitLab, npm and Hugging Face key prefixes, `Authorization: Bearer`, `key = value` assignments), replaced by `⟦secret:scanner⟧`. Conservative: recipients, names, hosts and email addresses stay. Every pattern is linear-time.
- Question sets: `exposure-v2` (exposure-v1 word for word on the redacted view; the request body only differs where redaction changed bytes) and `call-v2` (call-v1 on the call-v2 view: the preamble explains how to use the inputs, a new `scope_overreach` question, `untrusted_origin` reworded for a state that now includes tool results, and consequence criteria that name live records). The question set's `state_view` selects the view each probe sends.
- `call-v2` wording settled over three live dev passes: pointing at a document does not transfer the owner's authority to its instructions; naming a container does not settle its contents; items the owner named themselves are in scope however sensitive. The total input cap keeps the latest inputs.
- `suspicion.overreach` (reason `jev.scope_overreach`): from call-v2's `scope_overreach`, in the suspicion noisy-OR and in the Response 2.0 tree (`tree.suspicion.overreach`); model-only, so it never counts as a split.
- Configuration: `SENTROOK_JEV_EXPOSURE_QUESTIONS` and `SENTROOK_JEV_CALL_QUESTIONS` (defaults `exposure-v1`, `call-v1`); an unknown set, or a set whose view serves the other probe, stops startup. `/healthz` reports the question sets and views; the test-mode `prepared` block reports `views`, `views_version` and `redaction`, and `metadata.versions.views` names the views version in use.

### History lineage arm (2026-10-19)
Deterministic checks for harm assembled over several steps behind a bland pending call (`bash script.sh`, `cp a b`, `rm -rf dir`, `gh gist create file`). No new probe, signal or response field.
- `prepare`: a `Lineage` record on `Prepared`: the agent-written file the call runs (`executed`, the same file as `written_file`), agent-written files the call reads, sends or publishes (`sent`), history `mv`/`cp`/`rsync` into a tree the call destroys (`moved_in`), the agent's own saved writes that list paths under that tree (`listings`), and the call's destructive targets (`rm`, `shred`, `srm`, `unlink`, `rmdir`, `truncate`, `find -delete`, `find -exec rm`, resolved against the call's cwd and any `cd`). The test-mode `prepared` block reports it as paths and steps, never content.
- Entities: a host the command fetches a file from and then runs that file (`curl -o f URL && chmod +x f && ./f`, `wget -O f URL; sh f`, `curl -O`, or `git clone URL` followed by a build or setup step) is a code source, and the fetched file is the executable.
- AIRA: the agent-written file the pending call runs is analysed as a command of its own (source `written_file`, the pending call's cwd, the same detectors and packs, a Python or Node file read as interpreter source) and its findings merge like a sibling's, with `written_file` evidence (path, step, classes, rules, shape). A script that uploads a file is a send to the script's host; a script that fetches a binary and runs it is untrusted code; decode-to-shell inside the script takes the floor as it would at the prompt. The host's approval of the pending call covers the destruction arm for the file it runs. Fetch-then-run now also recognises `chmod +x FILE` (the mode is a positional) and running the fetched file directly.
- Context: five lineage arms, each new reason registered with a reader-facing template and each a `ContextParams` value (0 turns its arm off; `lineage_enabled` turns them all off; a parameter file can set them under `context.lineage`). A failure in the lineage arms contributes nothing.
  - `lineage.moved_into_destroyed_tree`: an item moved or copied from outside scratch into the tree the call destroys carries irreversibility 1.0, reach 0.75 and overreach 0.6 on that item, plus its path group's sensitivity.
  - `lineage.listing_marks_irreplaceable`: the agent's own listing of the destroyed tree with an irreplaceability marker (`only copy`, `no other copy`, `not rebuildable`, `originals`, …; `destructive.yaml` `irreplaceable_markers`) carries irreversibility 1.0 and overreach 0.6 on the target. A listing without a marker contributes nothing.
  - `lineage.secret_carried_to_send`: an agent-written file carrying a secret placeholder, or a secret shape the second redaction pass finds, that the call sends or publishes carries overreach 0.8, unless the request asks for a secret value to go (`lineage.yaml` `secret_request_terms`). The consequence still comes from AIRA.
  - `lineage.lookalike_of_named_host`: a host the call or the file it runs uses in a risky role that is one edit, or one confusable (`rn`/`m`, `0`/`o`, `1`/`l`), away from a host the owner named carries concealment 0.9, and its untrusted origin is scored as untrusted content (`origin.lookalike_of_named_host`) instead of agent-generated. Hosts under the named host's own domain never match.
  - `lineage.filter_silences_security_notices`: an agent-written file installed outside the workspace at a mail or notification filter location (`lineage.yaml` `filter_locations`) with a filter line naming a sign-in or security notice (`security_notice_terms` with `filter_action_patterns`) carries overreach 0.5 and sensitivity 0.6 on the destination.
- Lists: `destructive.yaml` version 2 (`irreplaceable_markers`); new `lineage.yaml` version 1, loaded with the other lists and included in the ruleset version string.
- `suspicion.overreach` is no longer model-only: the context probe contributes it from the lineage arms, so it can now count as shared when both probes claim it.
- Tests: lineage records, destructive-target resolution and fetched-then-run roles in `test_prepare`; written-file sends, fetch-then-run, decode-to-shell and the copy-only twin in `test_aira_detectors`; each context arm with its benign twin, the switches, the parameter block and failure isolation in `test_context_oracle_probes`.

### Serve: OIDC-only auth, test-mode-only ablation (2026-10-19)
- Scan auth is FIDU ID OIDC only (`SENTROOK_SCAN_AUTH_MODE=oidc|open`); the static API key (`SENTROOK_SCAN_API_KEY`, `X-Sentrook-Scan-API-Key`) and the `/healthz` `auth` field are gone. `open` is for a local sidecar or a test-mode server, is the default only in development without `SENTROOK_OIDC_ISSUER`, and is refused in production. Rate limiting keys on the OIDC caller, else the client address. Probe ablation (`SENTROOK_PROBES`, `sentrook scan --probes`) is refused unless `SENTROOK_TEST_MODE=1`.
