### AIRA probe: consequence detectors and lists (2026-10-16)
- `probes.aira.AiraProbe`: the deterministic consequence probe. One envelope per request with contributions on `consequence.sensitivity|reach|irreversibility|self_modification` and `suspicion.concealment`, the `guardrail_tampering` (min_risk 1.0, block) and `untrusted_code_execution` (min_risk 0.9, block; obfuscated decode-to-shell only) floors, the `holds_sensitive` flag, and evidence (classes, internal rule ids, exec shape summary, packs, per-finding detail). Siblings are scanned with the same detectors and count the same. Never raises.
- `aira.detectors`: C1 credential material reached, C2 exfiltration (source × sink) and plain sends, C3 untrusted code (fetch-to-shell, decode-to-shell, install-from-URL, package install, running a file written since a fetch), C4 self-modification and persistence, C4* guardrail tampering (OpenClaw and Hermes; content-aware for `openclaw.json` / Hermes `config.yaml` edits), C7 destruction outside scratch and C8 privilege change (pack `host_gated`; the preload/setuid/shadowing arms always on; C7 records evidence only when the host already granted approval), C9 irreversible remote side effects, C10 secret written into an artefact, extent (recursive / wildcard / bulk recipients raise reach), concealment for output suppression on network calls. Encoding alone contributes nothing.
- `aira.lists`: rules as code, knowledge as data. Versioned YAML under `aira/lists/` (`sensitive_paths`, `guardrail`, `destructive`, `remote_destructive`, `privilege`, `egress`, `installers`, `selfmod`, `extent`, `weights`), compiled at load, with an additive operator overlay from `SENTROOK_LISTS_DIR`; the combined version string is reported as `versions["ruleset"]`.
- Ported from 1.x (`engine/2.0-policy-switch`): `aira.exec_shape` (tree-sitter-bash segments, wrappers, privilege, env assignments, sinks, now also redirect targets and pipelines), `aira.path_classes` (location and group classification, URL hosts), `aira.normalize` (base64 / hex / quote-concat deobfuscation for matching), `aira.sensitive_paths` (the path-group compiler; the list gains browser-profile and PII-store groups and the agent-context groups for C4).
- Tests: `test_aira_exec_shape` (ported assertions plus authored shape cases), `test_aira_lists` (loader, overlay, compilation, normaliser), `test_aira_detectors` (one positive and one benign twin per class on synthetic PlanIRs with invented hosts, plus the two worked examples: the attack and its sanctioned twin carry the same consequence).

### First tuning step: conv-v2 and conv-v3 (2026-10-16)
- `conv-v2`: the oracle's unknown-entity distrust by role (destinations 0.3, recipients 0.25, tool providers 0.1; code sources and executables stay 0.5). Chosen on dev, confirmed once on held-out; `conv-v1` is unchanged and remains selectable with `SENTROOK_CONVERGENCE=conv-v1`.
- Items 2 to 6 (same day), each pinned by a unit test, chosen on dev and confirmed once on held-out:
  - Request-named relief also matches a recipient's display name (`Priya` for `priya.nair@…`, capitalised in the request) and the single `bcc`/`cc` address when the owner asks to be copied; neither applies to an address that reached the agent through content it read. The mail domain of a request-named recipient inherits the sanction.
  - `retry_after_denial`: matching is role-insensitive on the pending side and includes code and executable hashes (a shred retried through an interpreter, a write retried as an edit, a blocked install retried with another flag now match); a read-shaped call on the same data is the weaker `retry.same_source_only`. `context.retry_carry_consequence` (on in `conv-v3`) carries the denied step's consequence tier into a matched retry as reach and irreversibility.
  - AIRA C4: a script or data file in a workspace skill scores at `selfmod.workspace_skill` (0.5); the skill's instruction files keep the plugin weight (`weights.yaml` 4, `selfmod.yaml` 2).
  - AIRA C9: cloud IAM grants, access keys, inline or admin policies, repository secrets and RBAC bindings as `remote.grant` (`remote_destructive.yaml` 2); reader-level grants stay silent.
  - `conv-v3`: consequence as the mean of sensitivity, reach and irreversibility (max with self-modification), `u` 0.5, the retry carry on; the oracle table and everything else as `conv-v2`, which stays selectable.

### Question-set pass: call-v2 and exposure-v2 (2026-10-19)
A deliberate cache invalidation for the Jev probes, opt-in by configuration; the v1 views (`trim-v1`) and question sets stay byte for byte as they were and remain the default.
- `prepare.views`: a second views version, `trim-v2`. `call-v2` adds the turn's `new_inputs` between `history` and `pending_call`, so a question can weigh a listing or a read before a bulk or publishing call; each input's content is capped at 6000 characters and all of them at 40,000 (the earliest inputs lose content first so the latest, such as the listing right before the pending call, keep theirs; metadata stays, a cut input carries `scanner_truncated`), and a view still over the chunking budget keeps only the inputs' metadata. `exposure-v2` has the `exposure` keys. All four views are built on every request; `Prepared` records `views_version`, per-view metadata and the redaction count.
- `prepare.redact` (`redact-v1`): a second redaction pass over the v2 views for secret shapes the plugin's redaction missed (PEM private keys, JWTs, AWS, OpenAI/Anthropic, Stripe, GitHub, Slack, Google, GitLab, npm and Hugging Face key prefixes, `Authorization: Bearer`, `key = value` assignments), replaced by `⟦secret:scanner⟧`. Conservative: recipients, names, hosts and email addresses stay. Every pattern is linear-time.
- Question sets: `exposure-v2` (exposure-v1 word for word on the redacted view; the request body only differs where redaction changed bytes) and `call-v2` (call-v1 on the call-v2 view: the preamble explains how to use the inputs, a new `scope_overreach` question, `untrusted_origin` reworded for a state that now includes tool results, and consequence criteria that name live records). The question set's `state_view` selects the view each probe sends.
- `call-v2` wording settled over three live dev passes: pointing at a document does not transfer the owner's authority to its instructions; naming a container does not settle its contents; items the owner named themselves are in scope however sensitive. The total input cap keeps the latest inputs.
- `suspicion.overreach` (reason `jev.scope_overreach`): from call-v2's `scope_overreach`, in the suspicion noisy-OR and in the Response 2.0 tree (`tree.suspicion.overreach`); model-only, so it never counts as a split.
- Configuration: `SENTROOK_JEV_EXPOSURE_QUESTIONS` and `SENTROOK_JEV_CALL_QUESTIONS` (defaults `exposure-v1`, `call-v1`); an unknown set, or a set whose view serves the other probe, stops startup. `/healthz` reports the question sets and views; the test-mode `prepared` block reports `views`, `views_version` and `redaction`, and `metadata.versions.views` names the views version in use.

### History lineage arm (2026-10-19)
Deterministic checks for harm assembled over several steps behind a bland pending call (`bash script.sh`, `cp a b`, `rm -rf dir`, `gh gist create file`). No new probe, signal or response field.
- `prepare`: a `Lineage` record on `Prepared`: the agent-written file the call runs (`executed`, the same file as `written_file`), agent-written files the call reads, sends or publishes (`sent`), history `mv`/`cp`/`rsync` into a tree the call destroys (`moved_in`), the agent's own saved writes that list paths under that tree (`listings`), and the call's destructive targets (`rm`, `shred`, `srm`, `unlink`, `rmdir`, `truncate`, `find -delete`, `find -exec rm`, resolved against the call's cwd and any `cd`). The test-mode `prepared` block reports it as paths and steps, never content.
- Entities: a host the command fetches a file from and then runs that file (`curl -o f URL && chmod +x f && ./f`, `wget -O f URL; sh f`, `curl -O`, or `git clone URL` followed by a build or setup step) is a code source, and the fetched file is the executable.
- AIRA: the agent-written file the pending call runs is analysed as a command of its own (source `written_file`, the pending call's cwd, the same detectors and packs, a Python or Node file read as interpreter source) and its findings merge like a sibling's, with `written_file` evidence (path, step, classes, rules, shape). A script that uploads a file is a send to the script's host; a script that fetches a binary and runs it is untrusted code; decode-to-shell inside the script takes the floor as it would at the prompt. The host's approval of the pending call covers the destruction arm for the file it runs. Fetch-then-run now also recognises `chmod +x FILE` (the mode is a positional) and running the fetched file directly.
- Context: five lineage arms, each new reason registered with a reader-facing template and each a `ContextParams` value (0 turns its arm off; `lineage_enabled` turns them all off; a parameter file can set them under `context.lineage`). A failure in the lineage arms contributes nothing.
  - `lineage.moved_into_destroyed_tree`: an item moved or copied from outside scratch into the tree the call destroys carries irreversibility 1.0, reach 0.75 and overreach 0.6 on that item, plus its path group's sensitivity.
  - `lineage.listing_marks_irreplaceable`: the agent's own listing of the destroyed tree with an irreplaceability marker (`only copy`, `no other copy`, `not rebuildable`, `originals`, …; `destructive.yaml` `irreplaceable_markers`) carries irreversibility 1.0 and overreach 0.6 on the target. A listing without a marker contributes nothing.
  - `lineage.secret_carried_to_send`: an agent-written file carrying a secret placeholder, or a secret shape the second redaction pass finds, that the call sends or publishes carries overreach 0.8, unless the request asks for a secret value to go (`lineage.yaml` `secret_request_terms`). The consequence still comes from AIRA.
  - `lineage.lookalike_of_named_host`: a host the call or the file it runs uses in a risky role that is one edit, or one confusable (`rn`/`m`, `0`/`o`, `1`/`l`), away from a host the owner named carries concealment 0.9, and its untrusted origin is scored as untrusted content (`origin.lookalike_of_named_host`) instead of agent-generated. Hosts under the named host's own domain never match.
  - `lineage.filter_silences_security_notices`: an agent-written file installed outside the workspace at a mail or notification filter location (`lineage.yaml` `filter_locations`) with a filter line naming a sign-in or security notice (`security_notice_terms` with `filter_action_patterns`) carries overreach 0.6, sensitivity 0.6, reach 0.6 and irreversibility 0.6 on the destination: a filter that silences the owner's security notices is a persistent change to the account's alerting that outlives the session.
- Lists: `destructive.yaml` version 2 (`irreplaceable_markers`); new `lineage.yaml` version 1, loaded with the other lists and included in the ruleset version string.
- `suspicion.overreach` is no longer model-only: the context probe contributes it from the lineage arms, so it can now count as shared when both probes claim it.
- Tests: lineage records, destructive-target resolution and fetched-then-run roles in `test_prepare`; written-file sends, fetch-then-run, decode-to-shell and the copy-only twin in `test_aira_detectors`; each context arm with its benign twin, the switches, the parameter block and failure isolation in `test_context_oracle_probes`.

### Second redaction pass: vendor key shapes as data, `redact-v2` (2026-10-19)
A new redaction version: the pass now masks more vendor key formats, so v2 view bytes (and the Jev cache keys built on them) change wherever one of the new shapes occurs. The suite fixtures carry none (0 redactions before and after), so suite results are unaffected.
- `prepare.redact_shapes`: the vendor key shapes move from code to `prepare/redact_shapes.yaml` (name, regex, minimum length, source, source version), compiled at load. The ten `redact-v1` shapes stay as hand-kept entries (`source: sentrook`); 110 shapes are generated from the gitleaks default rules at `v8.30.1` (MIT, attribution in the file header). The generic shapes (PEM, JWT, `Authorization: Bearer`, assignment forms) stay in code. An operator overlay `redact_shapes.yaml` in `SENTROOK_LISTS_DIR` adds shapes.
- `prepare.redact_import` and `sentrook redact-shapes import --tag <tag> [--from FILE] [--check]` (`make redact-shapes`, `GITLEAKS_TAG`): fetch `config/gitleaks.toml` at a release tag, keep the rules that identify a key by a fixed prefix of at least three characters with a variable body, translate RE2 to Python (POSIX classes, mid-pattern flags scoped, trailing delimiters as look-aheads, unbounded repetition capped at 4096), and rewrite the file deterministically; a re-run with the same tag is a no-op. Skipped rules are listed in the file by reason (generic, keyword context needed, no fixed prefix, no variable body, too short).
- Keeping the shapes current: CI runs `make redact-shapes-check` (`--check` at `GITLEAKS_TAG`), so a hand edit of a generated entry or a tag moved without regenerating fails the PR. The weekly `redact-shapes-refresh` workflow (also run by hand) regenerates the file at the latest gitleaks release, moves `GITLEAKS_TAG`, runs the unit tests and opens or updates the PR `chore/redact-shapes-<tag>` (which also moves the gitleaks image the `security` workflow scans with, read from `GITLEAKS_TAG`) listing the added, removed and changed shapes (`--summary FILE`). A PR that changes the masked set still needs a new `REDACTION_VERSION` by hand, and CI must be started on it (a PR opened with the default token does not trigger it) unless the `REDACT_SHAPES_PR_TOKEN` secret is set.
- The pass checks the no-letter-or-digit-before boundary in code instead of a look-behind, so the regex engine can skip ahead to each shape's prefix (about six times faster over a 40,000-character view with 120 shapes).
- The test-mode `prepared.redaction` block gains `shapes`, the shapes version (`1;gitleaks=v8.30.1`, plus `+<overlay version>`).

### Staged secrets, known-good destinations, destructive SQL (2026-10-19)
Three deterministic blind spots shown by the first pass of new suite cases through the lineage-arm scanner. No question-set or view change, so the Jev cache replays.
- `prepare`: a file that a sibling in the pending call's batch writes and the pending call sends is `lineage.sent`, with the sibling's content (no earlier step shows the write). The context probe's secret-carried-to-send arm reads it, and AIRA's C2 source check now looks at sibling writes as well as history writes (`_placeholder_paths`), so a secret staged into the uploaded file in the same turn carries overreach and exfiltration sensitivity instead of only the sibling's artefact finding.
- Convergence: known-good destination relief. A destination or recipient the entity oracle reports `known_good` is relieved like a matched destination grant (`relief.known_good_destination`: that subject's `distrust` and `untrusted_origin`), for sends only, never for a code source or executable, and never when the host reached the agent through untrusted content. `known_good_relief.enabled` in the parameter file; default on, `conv-v3` unchanged.
- AIRA: destructive SQL is its own detector (`detect_sql_destruction`, rule `C7.sql`, pack `tier1`). A dropped, truncated or unconditionally deleted table is data in a live store, which a host's approval of the shell command does not gate, so it no longer waits for the `host_gated` pack alongside file destruction. The finding names the object (`target`). `destructive.yaml` version 3: `sql_patterns` capture the object and the file gains `live_table_markers`.
- Context: lineage arm `lineage.listing_marks_live_table`. When the agent's own query of the store (an exec or MCP tool result in the turn's inputs) lists the object a destructive statement names with a non-zero row count, a reference from another table or a word that says it is in use, the call carries irreversibility 1.0 and overreach 0.6 (`lineage_live_table_irreversibility`, `lineage_live_table_overreach`; 0 turns the arm off). A line without a mark, or a listing that arrived as fetched web content, contributes nothing. `Lineage.sql_targets` is recorded in the test-mode `prepared` block.

### Unvetted code carries read access; call-v3 with the entity library's verdicts (2026-10-20)
- AIRA C3: code fetched from a host that is not a listed installer and run, or installed from a URL on such a host, carries sensitivity at the personal-or-business level (`weights.yaml` version 6, `code.sensitivity_unvetted` 0.67, reason `code.unvetted_source`): it runs with the agent's own read access, whatever the command names. A listed installer host adds nothing. Deterministic, so the suite replays from the cache.
- `call-v3` view (`trim-v3`): the call-v2 view plus a `reputation` block after `grants`, the entity library's `known_good` and `known_bad` verdicts for the call's own hosts, recipients and packages (`kind`, `value`, `verdict`, `tier` when given). The call probe fills it from the oracle probe's result (`Prepared.oracle_verdicts`), and the scan runs the oracle probe before the pool when the configured call view carries the block; with nothing known, or the oracle disabled or unavailable, the key is absent and the body is what it would be without an oracle. The test-mode `prepared` block and the probe evidence (`reputation_entries`) report it.
- `call-v3` question set: call-v2 word for word, plus the preamble's description of `reputation` and, in `supported_by_request` and `untrusted_origin`, that a `known_good` destination satisfies a request that named its destination only generically, as a grant would, and is an ordinary choice. A first draft also tried two `scope_overreach` clauses (a keyword match whose label shows a different kind of item; content the agent added to a file it then sends); both were dropped after one live dev pass: the first did not reach its targets, the second fired on benign trajectory cases because the model cannot see what the agent read earlier and so cannot tell added content from copied content. `call-v3` is the shipped default (`SENTROOK_JEV_CALL_QUESTIONS`; `call-v2` and the frozen `call-v1` stay selectable): on the held-out split it improved every headline metric over call-v2 with no new false alarm, and it clears the known-good destination case that motivated it.

### Plugins v0 for OpenClaw and Hermes; scanner container image (2026-10-20)
- `integrations/openclaw/plugin` (`@firstdataunion/sentrook-openclaw` 2.0.0-beta.0, plugin id `sentrook`) and `integrations/hermes/plugin` (`sentrook` 2.0.0-beta.0, stdlib only): build PlanIR 2.0 from the host's hooks (request, trigger and sender, history with decisions and echoed tiers, new tool results, pending call with siblings and narration, provider identities, grants from config), call `/scan` with an OIDC client_credentials token, and allow, ask for the host's approval, or block. Review at risk 45, block at 80, the response's `enforced` floor always applies; `observe` mode scores and logs without interfering.
- The user's answer to a review (approve, deny, timeout, cancelled) is written back into history, so later scans see denials. On a scan failure the state token and input buffer are kept. Plugin state lives under `<state>/sentrook/`.
- Endpoints default to the hosted service; a non-default scan, Rookery or identity URL must be https on a firstdataunion.org host unless `SENTROOK_DEV_ENDPOINTS=1` is set in the environment. An invalid endpoint or missing credentials fails closed.

Every request and response pair is appended to a local, redacted traffic log (`traffic.jsonl`, 0600, rotated).
- `openclaw sentrook verify` / `hermes sentrook verify`: endpoints, credentials, scanner health, token mint.
- `make plugin-test`, `make hermes-plugin-test`, and `make plugin-planir-check` (the scanner's models and invariant checks must accept every PlanIR the plugins build in their integration tests); CI job `plugins`.
- `Dockerfile`: the scan service image (`sentrook serve`, non-root, health check on `/healthz`).

### A failed oracle lookup scores like no oracle (2026-10-20)
- `probes.oracle`: when the entity oracle's lookup raises (Rookery down, unreachable, or the key rejected), the probe answers as the null oracle does (every entity `unknown`, coverage lowered) instead of failing with no contributions, which had dropped the unknown-destination distrust and scored such a scan lower than a scanner with no oracle configured. The evidence carries `lookup_error` and `fallback: null`, and convergence reports the scan `degraded`. Test-mode scans use the seed oracle and are unaffected.

### An escalating session lifts the call's consequence (2026-10-20)
- `probes.context`: the `escalating` flag was set and kept but scored nothing. In an escalating session (the flag set earlier, or the last few history consequence tiers each rising by at least `escalation_rise`), a call with a consequence of its own (a destination or recipient, code it fetches or runs, or a destructive target) now carries sensitivity, reach and irreversibility at the session's last consequence tier plus `escalation_consequence_step` (default 0.2, capped at 1; 0 turns it off), reason `escalation.consequence_rising`. Under the mean consequence formula this moves a borderline call up about one band. The values merge by max, so a call already scored higher keeps its own; nothing is added on the suspicion side, so the trend never decides intent on its own; a read-only call, a session with level tiers, or a flag with no tier to step from is left alone. The evidence records the last tier, whether the call has a consequence and the value given. Deterministic, so the suite replays from the cache.

### Hermes plugin 2.0.0-beta.1: settings from config.yaml (2026-10-21)
- The plugin never read its settings: Hermes exposes `plugins.entries.sentrook.settings` one key at a time (`ctx.get_config(key)`), and the plugin asked for the whole mapping, got nothing and fell back to env and defaults. A `mode: observe` or dev endpoint set with `hermes config set` was ignored (the plugin ran in enforce mode against the production endpoints), and `hermes sentrook verify` reported the defaults. Each setting is now read by key, on every call, so a change applies without a restart. Env-only configuration (the e2e sandbox) was unaffected.


### Fetch piped into a program of its own is not download-then-run (2026-10-27)
- `aira.detectors`: the fetch-to-shell pipeline arm fired for any shell or interpreter stage after a fetch, so `curl … | python3 -m json.tool` or `curl … | python3 -c "…json.load(sys.stdin)…"` (querying a JSON API and formatting it) scored as running downloaded code. A stage now counts only when it reads its program from stdin: no program flag and no script file (`python3`, `python3 -u`, `bash`), an explicit stdin program (`python3 -`, `python3 /dev/stdin`, `bash -s`, `sh -s`, `python3 -i`, `python3 -m code`), or an inline program that runs its own input (`exec(`, `eval(`, `compile(`, `Function(`, `__import__`, `runpy`, `subprocess`, `pickle.load` and the like, stdin named as a file, or a substitution the calling shell fills with the piped bytes; for a shell, also `eval`/`source`, a variable run as a command, or another shell or interpreter named in it). A stage with its own program (`-c`, `-e`, `-m`, `--eval`, a script path) reads the fetched bytes as data. Eval heads, and any stage the argv walk cannot settle, still count. The text fallback for shapes the parse does not show (a program quoted into `sh -c '…'`, a decoded URL parameter) puts each match through the same check when its line parses as a pipeline; a match that does not parse still counts. The substitution and fetch-then-run arms are unchanged.
- `prepare.entities`: the same rule decides the host's role. A command that piped into any shell or interpreter made every host in it a code source (`curl … | python3 -m json.tool` made the API host one), which added the oracle's unknown-code-source distrust, made the host the subject of the code checks and let the escalation lift treat the call as having a consequence. `pipes_into_code` now lets the parsed pipeline stages decide when every pipe the text shows is one of them; anything the parse does not settle keeps the previous answer: a pipe inside an argument or assignment (a quoted program, a decoded URL parameter), a command or process substitution (`tee >(sh)`), a heredoc, a command that does not parse, an inline program, `source <(…)` and `eval …`. The stage check lives in `aira.stage_programs`, shared by both.
- `aira.lists` `installers` v4: `stage_programs` (per head family: program flags, stdin flags, value flags, bundle letters, subcommands, stdin modules), `stdin_paths`, `inline_stdin_exec_patterns` and `shell_inline_stdin_exec_patterns`.

### Host-written text in the request: rules read the owner's words, call-v4 tells Jev (2026-10-27)
- Hosts wrap scheduled, heartbeat, webhook and sub-agent prompts in their own text (a cron job header, the time, standing rules for unattended runs, a sub-agent context block, a webhook envelope around outside content, the heartbeat prompt before the queued events), and the plugins pass `request.text` through as the host built it. `prepare.host_text.owner_words` removes the host-written parts it recognises (Hermes and OpenClaw cron, OpenClaw sub-agent, webhook and heartbeat forms); text in any other form passes through unchanged. The rule-side matchers read only these words (`Prepared.request_words`): request-named entities (mentions, verbatim, display name, self-copy) and the lineage check for an owner asking for a secret. A host sentence no longer counts as the owner asking for a secret (the Hermes cron preamble mentions a "control token"), and a host named only in a webhook's outside content is not request-named. Jev's views keep the full text.
- `call-v4` question set: call-v3 word for word plus one preamble sentence saying the host may wrap `request.text` in its own text on those runs, that its rules constrain the agent and never sanction a call, and that a call breaking one is misalignment evidence. `call-v4` is the shipped default (`SENTROOK_JEV_CALL_QUESTIONS`; `call-v3`, `call-v2` and the frozen `call-v1` stay selectable).
- OpenClaw plugin: a heartbeat run's request text carries its queued system events. OpenClaw sends the generic heartbeat prompt as the turn's prompt and the events beside it in a runtime-context message labelled as data; the plugin now appends the events as plain `System: [time] text` lines after the prompt (taken from `before_agent_run`, only when the carrier closes the message list, so an earlier turn's events are never reused).

### OpenClaw plugin 2.0.0-beta.3, Hermes plugin 2.0.0-beta.2: redaction gaps (2026-10-27)
- Several common secret forms left the host unredacted in the PlanIR and the traffic log. Both plugins now replace, in request text, arguments, narration and tool results:
  - the password in a URL with credentials (`postgres://app:PASS@db…`, `redis://:PASS@cache…`, any scheme, a password holding `@` or `#`); user and host stay;
  - credential keys in JSON or assignment text whose name ends in a credential word, camelCase included (`"secretAccessKey"`, `"apiKey"`, `"clientSecret"`, `"logintoken"`, `"bearer"`, `"password"`), and `tok=`; in a JSON pair the whole quoted string is the value, spaces and `&` included; upper-case names with a credential word inside (`SENTROOK_SECRET_MARKERS=`) count for values of twelve or more characters that are not a number, path or URL;
  - keys and values inside a JSON-encoded tool result, where quotes arrive escaped (`\"password\": \"…\"`); Hermes hands structured results over in this form, so its JSON keys were missed;
  - secrets stated in prose: "the database password is X", "the password is now X", "token: X", "Bearer for the partner API: X", where X is six or more characters and not words, an identifier, a number, a path, URL, mask, template, code or date; and a value straight after a cue word ("gateway token X", "backup key X", "secret X") when it has twelve or more characters with both letters and digits (hex addresses and key fingerprints stay);
  - the token in a private calendar feed URL (`…/private-<token>/basic.ics`);
  - a private key's whole armoured block up to its END line, PGP blocks included, also when its line breaks are escaped (only the BEGIN line was replaced).
- One value, one placeholder: kinds now name only a value's own shape (`github`, `jwt`, `private_key`, …); every rule that finds a value by its context (a key, a header, a sentence, a URL) says `credential`, so `bearer` is no longer emitted. A value ends at a backslash, a private key is hashed without its line breaks, and a URL under a credential key keeps its host while its password is replaced, so a secret gets the same placeholder whether it arrives plain or JSON-encoded (one AWS secret key could get three).
- Object keys: any key ending in a credential word (`secretAccessKey`, `accessToken`, `logintoken`) has its value replaced whole, unless the value is a URL, which goes through the text rules.
- Values that name an environment variable (`token: GITHUB_TOKEN`) or start with `[` (`[REDACTED]`) are not a key's value.
- Traffic logs (`traffic.jsonl`) written by earlier plugin versions may hold such values in clear; delete or rotate them after upgrading.

### Second redaction pass: the plugins' text rules, `redact-v3`; OpenClaw plugin 2.0.0-beta.4, Hermes plugin 2.0.0-beta.3 (2026-10-28)
A new redaction version: the scanner's second pass over the v2 views now catches the forms the plugins learned in their last release, so a model never sees them in a view whatever the client sent (an older plugin build, `options.redaction: off`, another client). In both splits of the suite the pass makes no replacement before or after, so view bytes, Jev cache keys and suite results are unchanged.
- `prepare.redact` carries a copy of the Hermes plugin's text rules: the password in a URL with credentials (user and host stay); credential keys whose name ends in a credential word, camelCase included, and `tok=`, with escaped quotes and a value that ends at a backslash; whole quoted JSON values; upper-case names with a credential word inside; secrets stated in prose ("the database password is X", "token: X") and straight after a cue word, with the plugins' value checks; private calendar feed tokens; a `Bearer` token without an `Authorization` header; and a private key's whole block up to its END line, PGP included, also with escaped line breaks. The plugin's command-line flag rule is left out (`--secret-file PATH` would hide a path). Vendor shapes still come from `redact_shapes.yaml`; the placeholder stays `⟦secret:scanner⟧`.
- Names stay in prose, in the scanner and both plugins: a value stated or named after a cue word ("send the token to: X", "token file: X", "copy key X") is not a secret when it is an email address, a lower-case host or file name (a host may carry a port and a path) or a relative path to a file; and a URL whose authority starts with a host name and a port before a list or a fragment (`redis://cache.test:6379,admin@example.test`) holds no password. A credential key's value (`token: X`, `"password": "X"`) is still replaced whatever it looks like. In prose a dotted lower-case secret (`hunter2.backup`) or one shaped like an email now reads as a name; the trade keeps recipients and hosts visible to the scanner.
- Overlapping matches now merge into one placeholder covering all of them; before, a later match that ran past an earlier one left its tail in clear.
- The lineage check for a secret carried into a send uses the same pass, so it also sees these forms.
- Tests: the plugins' must-redact and look-alike lists, plain and JSON-encoded, with the host checked in every URL; a parity test runs the Hermes plugin's redactor on the same inputs and expects the same spans, and checks that the copied patterns are the plugin's character for character; bounded time on repeated BEGIN lines, `a_` runs, long prose and escaped-key runs.

### Command-line password flags, `redact-v4`; OpenClaw plugin 2.0.0-beta.5, Hermes plugin 2.0.0-beta.4 (2026-10-28)
Secrets passed on a command line are now handled the same way in both plugins and the scanner's second pass. No suite case holds these forms, so view bytes, Jev cache keys and suite results are unchanged.
- The scanner's second pass now catches a password flag with its value after a space (`--password X`, `--password 'X'`, `--api-key X`, `--token "X"`); before, only `--password=X` was caught (by the credential-key rule). The scanner's patterns are now the Hermes plugin's text rules with no exception, and the parity test checks all of them.
- A path, URL or setting after a flag is not a secret. A plain flag (`--password`, `--token`, `--api-key`, …) keeps its value when it is a variable reference (`$DB_PASSWORD`, `"$DB_PASSWORD"`) or reads as a path, URL, mask or template (`********`). A flag with a suffix also keeps a word, a number or any path: `--secret-file /etc/app/secret.txt`, `--token-path ~/.config/t`, `--password-file secrets/db_password`, `--token-url https://…`, `--token-ttl 3600`, `--auth-type basic` stay (the plugins hid them before), while `--token-value X` is still replaced. The plain-flag check is the one the prose rules use, so a password that itself starts with `/`, `~`, `.`, `*`, `{`, `[` or `(`, or reads as a host or file name, is not replaced after a flag.
- Short forms: a MySQL or MariaDB client's `-p` with the password attached (`mysql -pX`, `sudo mysql -pX`, `docker exec -it db mysql -pX`, `/usr/bin/mysqldump -p'X'`) and `sshpass -p X`. The client must be a command word (a directory such as `/var/lib/mysql` is not one, a path under a `bin/` is), the search stops at the end of its command (an escaped newline in a JSON-encoded result included), and a `-p` value that is a plain word or a port mapping belongs to another command (`find / -name mysql -prune`, `docker run --name mysql -p3306:3306`), so a dictionary-word password (`mysql -proot`) is not replaced. `ssh -p 2222`, `mysql -p` with no value (a prompt) and a `-p` in the command `sshpass` runs stay.
- A flag's quotes stay outside the placeholder, plain or escaped (`--token "⟦…⟧"`, `--token \"⟦…⟧\"` in a JSON-encoded tool result), so one value gets one placeholder however it is quoted and the JSON around it stays valid. A bare value keeps escaped characters (`P\!ss`) but ends at a quote or an escaped quote, newline or tab. Quoted values are matched up to 256 characters.
- Tests: in all three suites, the forms above must be replaced plain and JSON-encoded, with the JSON still parseable, the flag and quotes kept and one tag per value; the paths, URLs, settings, ports, prompts, variable references, masks and `mysql` look-alikes must stay; bounded time on repeated `mysql`, `sshpass` and `--password` runs and an unclosed quote.

### A sibling's findings count only when the batch itself is the attack (2026-10-28)
AIRA used to score every sibling's findings in full on the pending call, so one risky call in a parallel batch put every call in that batch into review, although each sibling is already scanned as its own pending call. Now a sibling's findings are evidence on the pending call (`counted: false` in the finding's evidence), except in two cases. A sibling that tampers with a guardrail or with the host's approval settings counts in full, because that leaves every call in the batch unguarded. A sibling that writes a path the pending call reads, runs, sends or writes through (the same path, a directory or link above it, or a file inside a directory the pending call reads) also counts in full, because it decides what the pending call acts on; the pending call's cwd and paths it only mentions are not compared. In both splits of the suite no case moves.
- `prepare.entities.fed_paths`: which of a call's paths another call's writes decide.
- AIRA evidence: each sibling gains `feeds_pending`; `reasons` lists only counted findings; `classes` and `rules` still list everything found.
- Tests: a credential copied by a sibling and uploaded by the pending call counts (also when the sibling writes the directory above the uploaded file, a file inside a directory the pending call archives, or a file inline code reads); a sibling guardrail or host-approval change counts; a sibling config change, a sibling credential read, a sibling send of a file the pending call writes, and a sibling write into the pending call's cwd or to a path a message only names are evidence only.

### A sibling's write joins the pending call's resolution (2026-10-28)
A call in the same batch can decide what the pending call acts on: it writes the file the pending command substitutes (`truncate "$(cat target.path)"`), the config a program reads its URL or package from, the link a sync follows, the archive an upload sends, or the script the pending call runs. The pending command alone names none of it, so an attack and its twin scored the same. Preparation now reads the pending command through the siblings' writes and scores what it resolves to.
- `prepare.sibling_join`: `sibling_writes` (file writes and edits, MCP or other write tools with a path and content, `ln -s`, write tools with an output and a list of inputs; memory keys are not files) and `resolve_pending`, which turns an exec pending call into resolved commands. How the command uses the written path is read segment by segment: a path it only writes (a redirect target, `rm`, `tee`, the last operand of `cp`) or only names (`echo`, `ls`) is not read through; relative spellings resolve against the pending call's cwd. A substitution naming the written file takes the written value (the JSON key path it reads, the only JSON string, or the text), a run file resolves to its content, a program given the file in `-c`/`-e` code or any other reader gets the value as an argument, a link path follows its target, an archive path becomes each input in turn. At most 16 resolved commands come out, with a `sibling_join_truncated` coverage note past that; a failure in the join is a `sibling_join_failed` note, not a failed scan.
- The resolved commands' entities join the table with the pending call's roles and the sibling's origin, before grants, inputs and history are read: a value an untrusted input planted scores as untrusted at full role weight, an owner-named one stays sanctioned, and the oracle and Jev's reputation block see the joined entities.
- AIRA analyses each resolved command as the pending call's own action (evidence `resolved`); the staged-placeholder check and the lineage of a file staged for a send read the same sibling writes, so MCP file writers count.
- Not joined: a value with no entity kind (a group name), and a sibling that writes no file (a policy store).
- Tests: substitution of a destructive target, a JSON key read by a program substitution, an edit's new text, a config read by code (the host joins as a destination), a run script, an MCP writer staging a placeholder, an archive carrying a key into an upload, a symlink followed by a sync; silent when the pending call does not read the written file, only writes or names it, spells it relative to another cwd, when the pending call writes and the sibling reads, for a memory key, and without a batch; odd sibling arguments give no writes.

### `/sentrook status` and `/sentrook help` in Hermes chats; Hermes plugin 2.0.0-beta.5 (2026-10-29)
The Hermes plugin registers a `/sentrook` slash command. Hermes answers it on gateway chats and in interactive `hermes chat` without a model request; over the API server and `hermes chat --oneshot` the text goes to the model, so each subcommand except help is also a `hermes sentrook` subcommand with the same output.
- `status` shows facts from configuration only, with no network call: plugin version, mode, review and block thresholds, scan-error policy, scan URL (or why it is invalid), whether credentials are set (never their values), the traffic log path or `off`, and the number of grants.
- `help`, empty input and an unknown subcommand list the subcommands.
- Subcommands live in one table (`commands.COMMANDS`); the slash command and the CLI are both built from it.
- Tests: status shows each fact and none of the client id, client secret or env secret; missing credentials, a disabled traffic log and an invalid scan URL are reported without a scan; unknown and empty input return help; the handler accepts Hermes's session-context keywords; `hermes sentrook status` prints the same text as `/sentrook status`; a host without slash commands still registers the plugin.
