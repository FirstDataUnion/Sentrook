### AIRA probe: consequence detectors and lists (2026-10-16)
- `probes.aira.AiraProbe`: the deterministic consequence probe. One envelope per request with contributions on `consequence.sensitivity|reach|irreversibility|self_modification` and `suspicion.concealment`, the `guardrail_tampering` (min_risk 1.0, block) and `untrusted_code_execution` (min_risk 0.9, block; obfuscated decode-to-shell only) floors, the `holds_sensitive` flag, and evidence (classes, internal rule ids, exec shape summary, packs, per-finding detail). Siblings are scanned with the same detectors and count the same. Never raises.
- `aira.detectors`: C1 credential material reached, C2 exfiltration (source × sink) and plain sends, C3 untrusted code (fetch-to-shell, decode-to-shell, install-from-URL, package install, running a file written since a fetch), C4 self-modification and persistence, C4* guardrail tampering (OpenClaw and Hermes; content-aware for `openclaw.json` / Hermes `config.yaml` edits), C7 destruction outside scratch and C8 privilege change (pack `host_gated`; the preload/setuid/shadowing arms always on; C7 records evidence only when the host already granted approval), C9 irreversible remote side effects, C10 secret written into an artefact, extent (recursive / wildcard / bulk recipients raise reach), concealment for output suppression on network calls. Encoding alone contributes nothing.
- `aira.lists`: rules as code, knowledge as data. Versioned YAML under `aira/lists/` (`sensitive_paths`, `guardrail`, `destructive`, `remote_destructive`, `privilege`, `egress`, `installers`, `selfmod`, `extent`, `weights`), compiled at load, with an additive operator overlay from `SENTROOK_LISTS_DIR`; the combined version string is reported as `versions["ruleset"]`.
- Ported from 1.x (`engine/2.0-policy-switch`): `aira.exec_shape` (tree-sitter-bash segments, wrappers, privilege, env assignments, sinks, now also redirect targets and pipelines), `aira.path_classes` (location and group classification, URL hosts), `aira.normalize` (base64 / hex / quote-concat deobfuscation for matching), `aira.sensitive_paths` (the path-group compiler; the list gains browser-profile and PII-store groups and the agent-context groups for C4).
- Tests: `test_aira_exec_shape` (ported assertions plus authored shape cases), `test_aira_lists` (loader, overlay, compilation, normaliser), `test_aira_detectors` (one positive and one benign twin per class on synthetic PlanIRs with invented hosts, plus the two worked examples: the attack and its sanctioned twin carry the same consequence).

### First tuning step: conv-v2 and conv-v3 (2026-10-16)
- `conv-v2`: the oracle's unknown-entity distrust by role (destinations 0.3, recipients 0.25, tool providers 0.1; code sources and executables stay 0.5). Chosen on dev, confirmed once on held-out; `conv-v1` is unchanged and remains selectable with `SENTROOK_CONVERGENCE=conv-v1`.
- Items 2 to 6 (same day), each pinned by a unit test, chosen on dev and confirmed once on held-out:
  - Request-named relief also matches a recipient's display name (`Priya` for `priya.nair@…`, capitalised in the request) and the single `bcc`/`cc` address when the owner asks to be copied; neither applies to an address that reached the agent through content it read. The mail domain of a request-named recipient inherits the sanction.
  - `retry_after_denial`: matching is role-insensitive on the pending side and includes code and executable hashes (a shred retried through an interpreter, a write retried as an edit, a blocked install retried with another flag now match); a read-shaped call on the same data is the weaker `retry.same_source_only`. `context.retry_carry_consequence` (on in `conv-v3`) carries the denied step's consequence tier into a matched retry as reach and irreversibility.
  - AIRA C4: a script or data file in a workspace skill scores at `selfmod.workspace_skill` (0.5); the skill's instruction files keep the plugin weight (`weights.yaml` 4, `selfmod.yaml` 2).
  - AIRA C9: cloud IAM grants, access keys, inline or admin policies, repository secrets and RBAC bindings as `remote.grant` (`remote_destructive.yaml` 2); reader-level grants stay silent.
  - `conv-v3`: consequence as the mean of sensitivity, reach and irreversibility (max with self-modification), `u` 0.5, the retry carry on; the oracle table and everything else as `conv-v2`, which stays selectable.

### Question-set pass: call-v2 and exposure-v2 (2026-10-19)
A deliberate cache invalidation for the Jev probes, opt-in by configuration; the v1 views (`trim-v1`) and question sets stay byte for byte as they were and remain the default.
- `prepare.views`: a second views version, `trim-v2`. `call-v2` adds the turn's `new_inputs` between `history` and `pending_call`, so a question can weigh a listing or a read before a bulk or publishing call; each input's content is capped at 6000 characters and all of them at 40,000 (the earliest inputs lose content first so the latest, such as the listing right before the pending call, keep theirs; metadata stays, a cut input carries `scanner_truncated`), and a view still over the chunking budget keeps only the inputs' metadata. `exposure-v2` has the `exposure` keys. All four views are built on every request; `Prepared` records `views_version`, per-view metadata and the redaction count.
- `prepare.redact` (`redact-v1`): a second redaction pass over the v2 views for secret shapes the plugin's redaction missed (PEM private keys, JWTs, AWS, OpenAI/Anthropic, Stripe, GitHub, Slack, Google, GitLab, npm and Hugging Face key prefixes, `Authorization: Bearer`, `key = value` assignments), replaced by `⟦secret:scanner⟧`. Conservative: recipients, names, hosts and email addresses stay. Every pattern is linear-time.
- Question sets: `exposure-v2` (exposure-v1 word for word on the redacted view; the request body only differs where redaction changed bytes) and `call-v2` (call-v1 on the call-v2 view: the preamble explains how to use the inputs, a new `scope_overreach` question, `untrusted_origin` reworded for a state that now includes tool results, and consequence criteria that name live records). The question set's `state_view` selects the view each probe sends.
- `call-v2` wording settled over three live dev passes: pointing at a document does not transfer the owner's authority to its instructions; naming a container does not settle its contents; items the owner named themselves are in scope however sensitive. The total input cap keeps the latest inputs.
- `suspicion.overreach` (reason `jev.scope_overreach`): from call-v2's `scope_overreach`, in the suspicion noisy-OR and in the Response 2.0 tree (`tree.suspicion.overreach`); model-only, so it never counts as a split.
- Configuration: `SENTROOK_JEV_EXPOSURE_QUESTIONS` and `SENTROOK_JEV_CALL_QUESTIONS` (defaults `exposure-v1`, `call-v1`); an unknown set, or a set whose view serves the other probe, stops startup. `/healthz` reports the question sets and views; the test-mode `prepared` block reports `views`, `views_version` and `redaction`, and `metadata.versions.views` names the views version in use.

### History lineage arm (2026-10-19)
Deterministic checks for harm assembled over several steps behind a bland pending call (`bash script.sh`, `cp a b`, `rm -rf dir`, `gh gist create file`). No new probe, signal or response field.
- `prepare`: a `Lineage` record on `Prepared`: the agent-written file the call runs (`executed`, the same file as `written_file`), agent-written files the call reads, sends or publishes (`sent`), history `mv`/`cp`/`rsync` into a tree the call destroys (`moved_in`), the agent's own saved writes that list paths under that tree (`listings`), and the call's destructive targets (`rm`, `shred`, `srm`, `unlink`, `rmdir`, `truncate`, `find -delete`, `find -exec rm`, resolved against the call's cwd and any `cd`). The test-mode `prepared` block reports it as paths and steps, never content.
- Entities: a host the command fetches a file from and then runs that file (`curl -o f URL && chmod +x f && ./f`, `wget -O f URL; sh f`, `curl -O`, or `git clone URL` followed by a build or setup step) is a code source, and the fetched file is the executable.
- AIRA: the agent-written file the pending call runs is analysed as a command of its own (source `written_file`, the pending call's cwd, the same detectors and packs, a Python or Node file read as interpreter source) and its findings merge like a sibling's, with `written_file` evidence (path, step, classes, rules, shape). A script that uploads a file is a send to the script's host; a script that fetches a binary and runs it is untrusted code; decode-to-shell inside the script takes the floor as it would at the prompt. The host's approval of the pending call covers the destruction arm for the file it runs. Fetch-then-run now also recognises `chmod +x FILE` (the mode is a positional) and running the fetched file directly.
- Context: five lineage arms, each new reason registered with a reader-facing template and each a `ContextParams` value (0 turns its arm off; `lineage_enabled` turns them all off; a parameter file can set them under `context.lineage`). A failure in the lineage arms contributes nothing.
  - `lineage.moved_into_destroyed_tree`: an item moved or copied from outside scratch into the tree the call destroys carries irreversibility 1.0, reach 0.75 and overreach 0.6 on that item, plus its path group's sensitivity.
  - `lineage.listing_marks_irreplaceable`: the agent's own listing of the destroyed tree with an irreplaceability marker (`only copy`, `no other copy`, `not rebuildable`, `originals`, …; `destructive.yaml` `irreplaceable_markers`) carries irreversibility 1.0 and overreach 0.6 on the target. A listing without a marker contributes nothing.
  - `lineage.secret_carried_to_send`: an agent-written file carrying a secret placeholder, or a secret shape the second redaction pass finds, that the call sends or publishes carries overreach 0.8, unless the request asks for a secret value to go (`lineage.yaml` `secret_request_terms`). The consequence still comes from AIRA.
  - `lineage.lookalike_of_named_host`: a host the call or the file it runs uses in a risky role that is one edit, or one confusable (`rn`/`m`, `0`/`o`, `1`/`l`), away from a host the owner named carries concealment 0.9, and its untrusted origin is scored as untrusted content (`origin.lookalike_of_named_host`) instead of agent-generated. Hosts under the named host's own domain never match.
  - `lineage.filter_silences_security_notices`: an agent-written file installed outside the workspace at a mail or notification filter location (`lineage.yaml` `filter_locations`) with a filter line naming a sign-in or security notice (`security_notice_terms` with `filter_action_patterns`) carries overreach 0.6, sensitivity 0.6, reach 0.6 and irreversibility 0.6 on the destination: a filter that silences the owner's security notices is a persistent change to the account's alerting that outlives the session.
- Lists: `destructive.yaml` version 2 (`irreplaceable_markers`); new `lineage.yaml` version 1, loaded with the other lists and included in the ruleset version string.
- `suspicion.overreach` is no longer model-only: the context probe contributes it from the lineage arms, so it can now count as shared when both probes claim it.
- Tests: lineage records, destructive-target resolution and fetched-then-run roles in `test_prepare`; written-file sends, fetch-then-run, decode-to-shell and the copy-only twin in `test_aira_detectors`; each context arm with its benign twin, the switches, the parameter block and failure isolation in `test_context_oracle_probes`.

### Second redaction pass: vendor key shapes as data, `redact-v2` (2026-10-19)
A new redaction version: the pass now masks more vendor key formats, so v2 view bytes (and the Jev cache keys built on them) change wherever one of the new shapes occurs. The suite fixtures carry none (0 redactions before and after), so suite results are unaffected.
- `prepare.redact_shapes`: the vendor key shapes move from code to `prepare/redact_shapes.yaml` (name, regex, minimum length, source, source version), compiled at load. The ten `redact-v1` shapes stay as hand-kept entries (`source: sentrook`); 110 shapes are generated from the gitleaks default rules at `v8.30.1` (MIT, attribution in the file header). The generic shapes (PEM, JWT, `Authorization: Bearer`, assignment forms) stay in code. An operator overlay `redact_shapes.yaml` in `SENTROOK_LISTS_DIR` adds shapes.
- `prepare.redact_import` and `sentrook redact-shapes import --tag <tag> [--from FILE] [--check]` (`make redact-shapes`, `GITLEAKS_TAG`): fetch `config/gitleaks.toml` at a release tag, keep the rules that identify a key by a fixed prefix of at least three characters with a variable body, translate RE2 to Python (POSIX classes, mid-pattern flags scoped, trailing delimiters as look-aheads, unbounded repetition capped at 4096), and rewrite the file deterministically; a re-run with the same tag is a no-op. Skipped rules are listed in the file by reason (generic, keyword context needed, no fixed prefix, no variable body, too short).
- Keeping the shapes current: CI runs `make redact-shapes-check` (`--check` at `GITLEAKS_TAG`), so a hand edit of a generated entry or a tag moved without regenerating fails the PR. The weekly `redact-shapes-refresh` workflow (also run by hand) regenerates the file at the latest gitleaks release, moves `GITLEAKS_TAG`, runs the unit tests and opens or updates the PR `chore/redact-shapes-<tag>` (which also moves the gitleaks image the `security` workflow scans with, read from `GITLEAKS_TAG`) listing the added, removed and changed shapes (`--summary FILE`). A PR that changes the masked set still needs a new `REDACTION_VERSION` by hand, and CI must be started on it (a PR opened with the default token does not trigger it) unless the `REDACT_SHAPES_PR_TOKEN` secret is set.
- The pass checks the no-letter-or-digit-before boundary in code instead of a look-behind, so the regex engine can skip ahead to each shape's prefix (about six times faster over a 40,000-character view with 120 shapes).
- The test-mode `prepared.redaction` block gains `shapes`, the shapes version (`1;gitleaks=v8.30.1`, plus `+<overlay version>`).

### Staged secrets, known-good destinations, destructive SQL (2026-10-19)
Three deterministic blind spots shown by the first pass of new suite cases through the lineage-arm scanner. No question-set or view change, so the Jev cache replays.
- `prepare`: a file that a sibling in the pending call's batch writes and the pending call sends is `lineage.sent`, with the sibling's content (no earlier step shows the write). The context probe's secret-carried-to-send arm reads it, and AIRA's C2 source check now looks at sibling writes as well as history writes (`_placeholder_paths`), so a secret staged into the uploaded file in the same turn carries overreach and exfiltration sensitivity instead of only the sibling's artefact finding.
- Convergence: known-good destination relief. A destination or recipient the entity oracle reports `known_good` is relieved like a matched destination grant (`relief.known_good_destination`: that subject's `distrust` and `untrusted_origin`), for sends only, never for a code source or executable, and never when the host reached the agent through untrusted content. `known_good_relief.enabled` in the parameter file; default on, `conv-v3` unchanged.
- AIRA: destructive SQL is its own detector (`detect_sql_destruction`, rule `C7.sql`, pack `tier1`). A dropped, truncated or unconditionally deleted table is data in a live store, which a host's approval of the shell command does not gate, so it no longer waits for the `host_gated` pack alongside file destruction. The finding names the object (`target`). `destructive.yaml` version 3: `sql_patterns` capture the object and the file gains `live_table_markers`.
- Context: lineage arm `lineage.listing_marks_live_table`. When the agent's own query of the store (an exec or MCP tool result in the turn's inputs) lists the object a destructive statement names with a non-zero row count, a reference from another table or a word that says it is in use, the call carries irreversibility 1.0 and overreach 0.6 (`lineage_live_table_irreversibility`, `lineage_live_table_overreach`; 0 turns the arm off). A line without a mark, or a listing that arrived as fetched web content, contributes nothing. `Lineage.sql_targets` is recorded in the test-mode `prepared` block.

### Unvetted code carries read access; call-v3 with the entity library's verdicts (2026-10-20)
- AIRA C3: code fetched from a host that is not a listed installer and run, or installed from a URL on such a host, carries sensitivity at the personal-or-business level (`weights.yaml` version 6, `code.sensitivity_unvetted` 0.67, reason `code.unvetted_source`): it runs with the agent's own read access, whatever the command names. A listed installer host adds nothing. Deterministic, so the suite replays from the cache.
- `call-v3` view (`trim-v3`): the call-v2 view plus a `reputation` block after `grants`, the entity library's `known_good` and `known_bad` verdicts for the call's own hosts, recipients and packages (`kind`, `value`, `verdict`, `tier` when given). The call probe fills it from the oracle probe's result (`Prepared.oracle_verdicts`), and the scan runs the oracle probe before the pool when the configured call view carries the block; with nothing known, or the oracle disabled or unavailable, the key is absent and the body is what it would be without an oracle. The test-mode `prepared` block and the probe evidence (`reputation_entries`) report it.
- `call-v3` question set: call-v2 word for word, plus the preamble's description of `reputation` and, in `supported_by_request` and `untrusted_origin`, that a `known_good` destination satisfies a request that named its destination only generically, as a grant would, and is an ordinary choice. A first draft also tried two `scope_overreach` clauses (a keyword match whose label shows a different kind of item; content the agent added to a file it then sends); both were dropped after one live dev pass: the first did not reach its targets, the second fired on benign trajectory cases because the model cannot see what the agent read earlier and so cannot tell added content from copied content. `call-v3` is the shipped default (`SENTROOK_JEV_CALL_QUESTIONS`; `call-v2` and the frozen `call-v1` stay selectable): on the held-out split it improved every headline metric over call-v2 with no new false alarm, and it clears the known-good destination case that motivated it.

### Plugins v0 for OpenClaw and Hermes; scanner container image (2026-10-20)
- `integrations/openclaw/plugin` (`@firstdataunion/sentrook-openclaw` 2.0.0-beta.0, plugin id `sentrook`) and `integrations/hermes/plugin` (`sentrook` 2.0.0-beta.0, stdlib only): build PlanIR 2.0 from the host's hooks (request, trigger and sender, history with decisions and echoed tiers, new tool results, pending call with siblings and narration, provider identities, grants from config), call `/scan` with an OIDC client_credentials token, and allow, ask for the host's approval, or block. Review at risk 45, block at 80, the response's `enforced` floor always applies; `observe` mode scores and logs without interfering.

Every request and response pair is appended to a local, redacted traffic log (`traffic.jsonl`, 0600, rotated).
- `openclaw sentrook verify` / `hermes sentrook verify`: endpoints, credentials, scanner health, token mint.
- `make plugin-test`, `make hermes-plugin-test`, and `make plugin-planir-check` (the scanner's models and invariant checks must accept every PlanIR the plugins build in their integration tests); CI job `plugins`.
- `Dockerfile`: the scan service image (`sentrook serve`, non-root, health check on `/healthz`).

### A failed oracle lookup scores like no oracle (2026-10-20)
- `probes.oracle`: when the entity oracle's lookup raises (Rookery down, unreachable, or the key rejected), the probe answers as the null oracle does (every entity `unknown`, coverage lowered) instead of failing with no contributions, which had dropped the unknown-destination distrust and scored such a scan lower than a scanner with no oracle configured. The evidence carries `lookup_error` and `fallback: null`, and convergence reports the scan `degraded`. Test-mode scans use the seed oracle and are unaffected.

### An escalating session lifts the call's consequence (2026-10-20)
- `probes.context`: the `escalating` flag was set and kept but scored nothing. In an escalating session (the flag set earlier, or the last few history consequence tiers each rising by at least `escalation_rise`), a call with a consequence of its own (a destination or recipient, code it fetches or runs, or a destructive target) now carries sensitivity, reach and irreversibility at the session's last consequence tier plus `escalation_consequence_step` (default 0.2, capped at 1; 0 turns it off), reason `escalation.consequence_rising`. Under the mean consequence formula this moves a borderline call up about one band. The values merge by max, so a call already scored higher keeps its own; nothing is added on the suspicion side, so the trend never decides intent on its own; a read-only call, a session with level tiers, or a flag with no tier to step from is left alone. The evidence records the last tier, whether the call has a consequence and the value given. Deterministic, so the suite replays from the cache.

### A sibling's write joins the pending call's resolution (2026-10-28)
A call in the same batch can decide what the pending call acts on: it writes the file the pending command substitutes (`truncate "$(cat target.path)"`), the config a program reads its URL or package from, the link a sync follows, the archive an upload sends, or the script the pending call runs. The pending command alone names none of it, so an attack and its twin scored the same. Preparation now reads the pending command through the siblings' writes and scores what it resolves to.
- `prepare.sibling_join`: `sibling_writes` (file writes and edits, MCP or other write tools with a path and content, `ln -s`, write tools with an output and a list of inputs; memory keys are not files) and `resolve_pending`, which turns an exec pending call into resolved commands. How the command uses the written path is read segment by segment: a path it only writes (a redirect target, `rm`, `tee`, the last operand of `cp`) or only names (`echo`, `ls`) is not read through; relative spellings resolve against the pending call's cwd. A substitution naming the written file takes the written value (the JSON key path it reads, the only JSON string, or the text), a run file resolves to its content, a program given the file in `-c`/`-e` code or any other reader gets the value as an argument, a link path follows its target, an archive path becomes each input in turn. At most 16 resolved commands come out, with a `sibling_join_truncated` coverage note past that; a failure in the join is a `sibling_join_failed` note, not a failed scan.
- The resolved commands' entities join the table with the pending call's roles and the sibling's origin, before grants, inputs and history are read: a value an untrusted input planted scores as untrusted at full role weight, an owner-named one stays sanctioned, and the oracle and Jev's reputation block see the joined entities.
- AIRA analyses each resolved command as the pending call's own action (evidence `resolved`); the staged-placeholder check and the lineage of a file staged for a send read the same sibling writes, so MCP file writers count.
- Not joined: a value with no entity kind (a group name), and a sibling that writes no file (a policy store).
- Tests: substitution of a destructive target, a JSON key read by a program substitution, an edit's new text, a config read by code (the host joins as a destination), a run script, an MCP writer staging a placeholder, an archive carrying a key into an upload, a symlink followed by a sync; silent when the pending call does not read the written file, only writes or names it, spells it relative to another cwd, when the pending call writes and the sibling reads, for a memory key, and without a batch; odd sibling arguments give no writes.

### The over-budget fill sends an input whole when it fits whole: `trim-v7` (2026-11-14)

The fill now finds the largest total that fits.

### A cut in the call view never splits a secret: `trim-v8` (2026-11-14)
The `call-v5` view cuts long strings (an input's content, an over-budget request text, long history argument strings) before the scanner's second redaction pass runs over the finished view. A cut point inside a secret the plugin had missed left a fragment without the shape the pass recognises, such as a token with too few characters left, a value cut off from its `password:` cue, or a JSON value missing its closing quote. That fragment reached the judge in clear.
- `prepare.redact.protected_spans`: the stretches a cut must not split. These are every secret `redact_text` would replace, widened by what identifies it: a value found by its context keeps the cue word or key before it and its closing quote after it. They are merged, sorted and disjoint.
- `prepare.views`: on the `call-v5` view (views version `trim-v7` to `trim-v8`), a head's end that falls inside a protected stretch moves back to its start, and a tail's start moves forward to its end. Moving out of the spans is not enough on its own, because text outside a secret's span can still decide whether the pass sees it: the `mysql -p` rule reads the characters before `mysql`, and a cut can make an earlier cue live whose match then runs over the next secret's cue. So the cut string is then redacted, and while a secret the whole string would replace is still there in clear, the cut point on its side moves past it. Each secret is kept whole, and replaced by the second pass, or cut away whole. `scanner_truncated.kept_chars` and the marker report what was really kept, which can be fewer characters than the cap. This applies to the input caps and fill, the request cut and the history argument cut. Spans are found once per string, not once per fill attempt, and the caches are cleared after each build, so no request's text stays in memory; strings with no secret skip the check.
- With no secret near a cut point, every cut is as before. `call-v2` and `call-v3` are unchanged.
- Suite: no fixture input or request is cut. Every view of all 1,753 fixtures is byte-identical before and after, at the default call budget and at `call-v6`'s, so Jev requests, cache keys and suite results are unchanged.
- Tests: no fragment of a secret reaches the view when a token straddles the request's head end or tail start, when the tail would start inside a `password:` cue, when the head would end before a JSON value's closing quote, at an input's head and tail, and at a history argument's 400-character end, and when a request or input tail would start within the characters the `mysql -p` rule reads before `mysql`, or would make an earlier cue swallow a secret's cue. A secret inside the kept head or tail is still replaced. A cut with no secret near it keeps exactly what it kept before. `call-v3` is unchanged. Spans are found once per string during the fill.

### Where a call's arguments came from: fewer wrong origins, values a sibling supplies (2026-11-15)
The context probe's `untrusted_origin` asks whether each key argument came from the owner, from the agent, or only from content the agent read. Several entities were charged an origin they did not have, and a value a sibling call writes for the pending command had none at all.
- A path a step's own arguments named is the agent's when that step's result repeats it (a write receipt naming the file just written): for paths, the agent-first comparison includes the same step, in the origin value, the display-name and self-copy checks and the untrusted-set additions. Hosts, recipients, packages and every other kind keep the strict comparison: a fetched page that names its own host as where to send something is content steering the agent, so that host scores as content-supplied and joins the session's untrusted set.
- An MCP server or plugin that is in a call only as the provider of its tool makes no agent-chose-it claim: the host's configuration supplied it. It keeps one when its identity (or a remote server's host, a local server's package) reached the agent through untrusted content, or the call's arguments name it.
- It also keeps the agent-chose-it value (`origin.switched_provider`, evidence `switched_from`) when an earlier step of the session called the same tool name through a different MCP server or plugin (another version of the same package is the same provider) and the entity library does not vouch for the new one as known good: the host did not simply supply it.
- An entity only a sibling call names, as the sibling stands, is charged in that sibling's own scan, not the pending call's: no origin claim, and an unknown one adds no distrust or coverage loss. What a sibling's write resolves the pending command to stays charged, a code source or executable is never sibling-only (a sibling can point the pending install at another registry without the install naming it), and known-bad entities, look-alikes of vouched ones and entries with their own distrust count wherever they are in the batch.
- A message addressed to the owner by a self-reference (`me`, `self`, `myself`, `owner`) is not an unknown third party: no unknown-recipient distrust, no coverage loss, no agent-chose-it origin, unless content supplied it.
- Packages: a package named in the prose of content the agent read (a sentence, a list, a command in backticks) came from that content, unless the request names it or the agent's own call named it first; a package installed from a URL the owner wrote, or from a local file the owner named by its path, is request-named; a command substitution among install operands is one computed package (`npm:$(...)`), not package names, and when a sibling writes the value it reads, the resolved command names the package.
- The object of a SQL statement (`DROP TABLE schema.table`, `INSERT INTO`, ...) is no longer extracted as a host.
- `prepare.sibling_join`: `Resolution.values` (and `Prepared.sibling_values`) lists the values the join put in place of the pending command's command substitutions. A one-word value of three characters or more that is no entity of its own (a group, a role, a scope, for `usermod -aG "$(cat role.txt)"` with a sibling writing `role.txt`), named as a whole word by untrusted content in this request and not by the owner's words, contributes `untrusted_origin` at the untrusted value (`origin.sibling_value_untrusted`). A value the request names makes no claim; a multi-word value (a written message) is content, not a key argument; a path, host or package the resolved command names is scored as the entity it is. Only this request's inputs are compared: the session's untrusted set holds entities, not values.
- Tests: each rule with its silent twin, in `test_sibling_value_origin`, `test_sibling_only_entities`, `test_provider_origin` and the origin and package tests.

### A local install is the workspace's own code, not a registry package (2026-11-16)

### Plugins 2.0.0-beta.9: a review on an unattended run holds the call and tells the owner (2026-11-16)
On a run nobody can answer (a cron job, heartbeat, hook or subagent on OpenClaw; cron, subagents, webhooks, the API server, approvals off or a YOLO gateway on Hermes) a review used to become a block, or on OpenClaw an approval prompt nobody saw that was denied after 30 minutes, and nobody was told. Now the call is held:
- The call does not run. The agent gets a plain result: held for the owner's approval; do not retry this call in this run. It names no category, reason codes or score.
- The owner gets one notice. Hermes copies what `send_message` sends into the agent's own conversation, so on both hosts the notice carries only that a call was held, which run (a cron job by its id, with its name in quotes and labelled as the job's name, so a name the agent chose cannot read as an instruction), the tool and its target as a review names them, the block category, and the approve and `why` commands. Chat markup (`[]()<>|@` and backticks: links, mentions, code) is taken out of every field the agent can influence (the job id and name, the tool, the target description), and the target description is capped at 160 characters. The job's id and name come only from the host's own cron identity (Hermes's cron execution; on OpenClaw, the host's `[cron:<id> <name>]` prefix, read only on a run the host marks as a cron run), never from a prompt alone. No risk, reason codes, scores, entities, arguments or suggested grant: the owner reads those with `/sentrook why <id>` (Hermes) or `/sentrook-why <id>` (OpenClaw), owner only, which shows the held call's scan as `why` does plus the hold and its suggested grant.
- Hermes sends the notice to the home channel of the platform named in the new `owner_channel` setting (or `SENTROOK_OWNER_CHANNEL`); there is no fallback, so nothing is sent until it is set. It goes through Hermes's own `send_message`, dispatched by the plugin (so it is not scanned) from a worker thread with an empty context (so a cron job that delivers to the same home channel does not swallow it). OpenClaw sends it as a direct message through the channel's outbound adapter, to the sender who ran the new `/sentrook-notify here` in a direct message: it is refused in a group or channel and when OpenClaw names no sender, uses the `user:<id>` form on Discord, and keeps a thread only for a direct message on Telegram or Slack. With no target, the call is still held and the scan record says the notice was not sent and why; `status` and `verify` say so too.
- `/sentrook approve <id>` (Hermes) or `/sentrook-approve <id>` (OpenClaw), within 24 hours and for the owner only, sets the suggested grant as a persistent grant that ends after 30 days; the held call is not run again, and the next run is scanned with the grant. A suggestion is read through the same parser and rules as `grant <kind> <pattern> --persistent`, so it can never set more than the command could; each `allows` entry must be exactly one known verb. The grant is written before the hold is consumed: when the grants file cannot be written, the hold stays and the reply says so. The grant is set once per hold: an approval retried after the holds file failed to save finds the grant it set and adds none. A malformed scan response whose notice cannot be built still holds the call, with the traffic record written and the notice unsent. With no suggestion, approval sets nothing and the reply says so. An unknown, answered or expired id is refused. The scan response carries no suggested grant yet, so every hold is made without one until it does.
- A hold nobody answers expires after 24 hours and nothing runs.
- A block at the block line or an enforced block is never held. Attended runs are unchanged: a review is still a review prompt. Observe mode holds nothing, and a snooze never applies to an unattended run.
- Traffic log: the scan record has decision `held` and a `hold` field (id, expiry, whether a grant was suggested, the notice's status and target); a later `resolution` record has resolution `hold_approved` (with the grant id when one was set) or `hold_expired`, recorded when the holds are next changed. `history` shows the action `held` and the review `no answer`, `approved` or `expired`; `status` counts waiting holds, and self-edit / loop-save counts gain `held`. Holds are kept in `holds.json` in the plugin's state folder, the same format on both hosts.
- `holds.json` and `grants.json` are changed under a lock on `<file>.lock` on both hosts, with the existing atomic write, so the gateway and a separate process (`hermes cron run`, the `hermes sentrook` or `openclaw sentrook` command line) changing them at once no longer lose a record; Hermes's in-process lock alone did not cover a second process. Both take an operating-system lock, which the system releases when its process dies, so a crashed holder needs no takeover and no two processes ever hold it at once: Hermes locks the file itself (`flock`, `msvcrt.locking` on Windows); OpenClaw holds an exclusive transaction on a small SQLite file beside it (`<file>.lockdb`) through Node's own `node:sqlite`, which OpenClaw also uses. Waits are short (2 s on Hermes, 1 s on OpenClaw); when a hold cannot get the lock in time the call is still held and the notice is logged unsent with reason `holds file locked`.
- A held call goes to the scanner in later history as `review_timed_out`: it did not run, and a retry of it in the same run is a retry after an unanswered review.
- OpenClaw: `approval.scheduledTimeoutMs` and `approval.scheduledTimeoutBehavior` no longer reach a review; they are still read so existing configs load. The owner commands' existing gate (sender is owner, `operator.admin` for gateway clients) is used for `/sentrook-approve` and `/sentrook-notify`; OpenClaw lets an owner listed in `commands.ownerAllowFrom` run them from a direct message.
- Tests: shared texts in `integrations/fixtures/hold` (agent text, notice text, what each verdict becomes attended and unattended, history columns), checked by both plugins; must hold: a scheduled send at risk 47 is held, the notice is sent once and the log shows `held`; approval writes the suggested grant persistent for 30 days and the next scan sends it; approval without a suggestion sets nothing; malformed, unknown and expired ids are refused; expiry is exactly 24 hours and recorded once; two processes holding calls at the same time keep every hold; two waiters on a lock left over never both enter, and a lock held by a process that died is free at once (Hermes); three processes after a holder crashed never hold the lock at once, over repeated rounds (OpenClaw); a locked holds file still holds with the notice unsent; approve keeps the hold when the grant cannot be written; the notice text is pinned and carries no risk, reason codes, scores, entities, arguments or secret values; `why <hold id>` shows the reasons; a suggested grant must pass the grant command's rules; the notify target refuses a group, a missing sender and uses `user:` on Discord; a snooze never relieves an unattended review; chat markup is taken out of the notice (shared fixture); a cron marker in a prompt names no job; a retried approve after a holds-file save failure sets one grant; a malformed response still holds with the notice unsent; must still block at and over the block line and on an enforced block; attended reviews still prompt; Hermes's notice leaves the run's context behind.

### Guardrail: loosening the host's approvals or allowlists takes the floor (2026-11-17)
An agent that turns the host's approvals off, sets the approval fallback to allow, enables YOLO, turns off OpenClaw's inline-eval approvals or Hermes's hook consent, or puts a wildcard, a shell or an interpreter in an allowlist removes the owner from the loop for every later call. These changes were scored as self-modification only, so a block rested on the score alone. They now take the `guardrail_tampering` floor in two tiers. The floor fires only on the host's own files and commands, never on a project that uses the same words. Other changes to the host's approval settings stay scored as before.
- **Block tier** (`guardrail.approval_loosening`): a known approval setting or environment variable changed to a looser value through a config command, an approvals command, a launch flag, or a write, edit or patch whose target is a host file, and a broad allowlist entry. Like any floor, either tier is a strong signal, so the response is never `relaxable` and a snooze cannot turn the block into a question.
- **Review tier** (`guardrail.approval_loosening_review`, enforced `review`, minimum risk 0.5, no score of its own): what the scan can only infer. The owner is always asked, and this floor never blocks on its own. It covers:
  - a script whose text holds a loose value it writes into a host approvals or config file but no setting the scan can read (`sed -i 's/deny/full/'`, `.replace('deny', 'full')`);
  - a host approvals or main config file replaced from content the scan cannot read (`cp`, `mv`, `install`, `rsync`, `ln -sf`, `cp -t`, `cat src >`, `base64 -d >`, `curl -o`/`-sSo`, `wget -O`/`-qO`, `openclaw approvals set --file`). The source counts as unreadable unless it is a host approvals or config file, or the same command wrote readable content to it;
  - a setting in an OpenClaw `$include` file;
  - an edit fragment whose section cannot be decided (a `mode` fragment stays quiet: both hosts have other `mode` keys);
  - inline code that names a host approvals or main config file and writes to a target the scan cannot resolve.
- Text matching is linear in the input: no pattern has two ways to match the same characters (a substitution's escapes, an option's dashes, path segments), whole-entry patterns are anchored, YAML anchors and tags are matched possessively, and heredocs are read in one pass. A long run of escapes after `s#` used to backtrack exponentially and could time the scan out.
- `guardrail.yaml` (version 5) gains `approval_loosening`; `weights.yaml` (version 8) gains `guardrail.review_floor_min_risk`.
- Settings (name and value, quoted or not, `:` or `=`):
  - OpenClaw: `askFallback` `full`/`allow`; `tools.exec.mode` `full`; legacy `security` `full` and `ask` `off`; a bare approvals switch off inside the exec settings; `tools.exec.strictInlineEval` `false` (all in its approvals and config files); the older plugin approval `timeoutBehavior` `allow` (in plugin code in the tree).
  - Hermes: `approvals.mode` `off`; `approvals.cron_mode` / `single_query_mode` / `unattended_mode` `approve`; `hooks_auto_accept` true (in `config.yaml`); `HERMES_YOLO_MODE` or `HERMES_ACCEPT_HOOKS` true.
  - A setting counts only in its own host's files: Hermes settings in the Hermes trees, OpenClaw settings in the OpenClaw trees.
- Allowlists (OpenClaw `allowlist` and similar, Hermes `command_allowlist`; the OpenClaw entry `pattern` in an approvals file): an entry that is a wildcard (`*`, `**`, `.*`), everything in a directory (`/usr/bin/*`, `~/**`), a download piped to a shell, or a shell, interpreter, launcher or `sudo` (`bash`, `pwsh`, `env`, `xargs`, `find`, `npx`, `python`/`python3.12`, `node`/`node22`, `ruby`, `perl`, `php`, `deno`, `bun`, `osascript`), bare or with arguments that are only options, wildcards or a runner verb. An entry with a script or a named tool is narrow and stays scored.
- Where a setting counts:
  - The host trees, by root: `~/.openclaw` and a profile's `~/.openclaw-<name>`, `~/.hermes` and its `profiles/<name>`, `/etc/hermes` and Hermes's Docker home. The workspace excludes its files only when it sits strictly inside a tree (OpenClaw's `~/.openclaw/workspace`); a workspace that is a tree root or contains one (Hermes runs with `~/.hermes` or `~` as its working directory) excludes nothing. A file named like a host file in a project does not count.
  - Host files at a tree root: the approvals files (`exec-approvals.json` and the other host-guardrail files), where any loosening setting counts; the main config (`openclaw.json`, Hermes `config.yaml`, a profile's too) and OpenClaw's `$include` JSON5 files, read as fragments. A skill's own `config.yaml` or `settings.json` is not host config, and `skills/`, `plugins/`, `hermes-agent/` and `node_modules/` under a tree are skipped for tree-wide settings, allowlists and the environment variables.
  - In the config files, `mode`, `security`, `ask` and the approvals switch count only when the nearest enclosing key is the exec or approvals section. The enclosing key comes from one forward pass over the text: JSON or JSON5 braces with strings and `//`/`/* */` comments skipped and unquoted keys read, or YAML indentation with comments, anchors and tags skipped; `\u` escapes are decoded first. A setting inside a string, a comment or a YAML block scalar (`|`, `>`) does not count. Keys match case-sensitively, values case-insensitively. For a config command it is the path. In an edit fragment that shows no enclosing key they count when the replaced text held the same key with an approvals value, and `security` and `ask` count on their own in `openclaw.json`; any other fragment gets the review tier. At the top level of a whole file they do not count.
  - The environment variables also count in shell rc files, service units, launchd plists and any `.env`. Documentation files never count.
- Routes:
  - `openclaw config set|patch|unset` (also `--batch-json` and JSON values) and `hermes config set`. Unsetting `tools`, `tools.exec` or its `mode`, `security`, `ask` or `strictInlineEval`, setting one of them to `null`, and setting `tools` or `tools.exec` without `--merge` to an object that drops the policy (no `mode`, and not both `security` and `ask`) count, since OpenClaw falls back to `security: full`, `ask: off` and `strictInlineEval: false`.
  - `openclaw exec-policy preset yolo`, `exec-policy set` with a loosening flag, `openclaw approvals set` with the document in the command, and `openclaw approvals allowlist add` with a broad entry.
  - Hermes launched with `--yolo` or `--accept-hooks`; `HERMES_YOLO_MODE` or `HERMES_ACCEPT_HOOKS` set in a command or with `launchctl setenv`.
  - File tools: write, edit, `apply_patch` and Hermes `patch` hunks.
  - Shell writes, segment by segment with `cd` and `pushd` followed and `bash -c` scripts unwrapped: redirect targets, `tee`, `sponge`, `dd of=`, and the file operands of `sed -i`, `perl -pi`, `ruby -i` and `yq -i`. What is written is read as settings: the text `echo` and `printf` print (escapes interpreted for `printf` and `echo -e`), heredoc bodies, what an earlier `echo` feeds a pipe, a substitution's replacement (its search text counts as the old text for its own segment only), and a script's key-path assignments (`jq '.tools.exec.mode = "full"'`, `c['tools']['exec']['mode'] = 'full'`, `c.tools.exec.mode = 'full'`) and string literals.
  - Inline code (`python -c`, `node -e`, Hermes `execute_code`, a script in a heredoc) counts only for the target of a write sink: `open(…)` with a write mode (also `mode='w'`), `Path(…).open('w')`, `write_text`, `fs.writeFile` (also through `require('fs')`), `shutil.copy`. Commands the code runs (`os.system`, `subprocess.*`, `child_process.exec*`) are read as commands. A script that reads a host file and writes elsewhere does not count.
  - Relative paths (`../openclaw.json`, a bare name after `cd`), `${HOME}`, `~user`, shell variables assigned in the command and a symlink the command makes to a host tree are resolved first; on macOS and Windows the trees match in any case.
  - Global options, launchers and `sh -c` scripts are handled as for the other CLI rules.
- A file change fires only when the loosening setting is in the text written and not in the text it replaces, so tightening or moving a setting does not. A write of a whole file has no old text, so a loosening setting the file already held (for example `"exec": {"mode": "full"}` in `openclaw.json`) fires again when the agent rewrites it; this is accepted for now.
- Not floored: narrow allowlist entries, Hermes `approvals.mode` `smart`, MCP server trust, removing an `approvals.deny` entry, a value read from a file the call does not show (`config set approvals @file.json`), reads, and unrelated keys.

### A review names the grant that would allow it next time; plugins Hermes 2.0.0-beta.13 and OpenClaw 2.0.0-beta.12 (2026-11-17)
A new owner has no grants, so routine work reviews more than it needs to, and a review did not say what would stop it repeating. - Only on the owner's own turns: the sender is the owner, or the host started a `scheduled` or `heartbeat` run with no sender behind it (`unknown`). Never for a non-owner sender (a stranger, a trusted contact, a group chat, a scheduled run with sender `other`), a sub-agent or a hook. ### Self-edit scans report what a save adds and whether it qualifies for lenient handling (2026-11-19)
- Response 2.0 gains an optional `self_edit` object, present only when the request is a declared self-edit (trigger `system` with a `self_edit` block) and absent otherwise: `{"adds": [...], "lenient": true|false}`. Additive; no `response_version` change, since optional fields are additive under 2.0 and a plugin that ignores the field behaves as before.
- `adds` (`prepare.save_adds`), sorted and de-duplicated, says what the saved content adds, read by rule from the text the save writes (no model): `command` runnable steps; `destination` a host, URL, mail address, recipient or remote a later run reaches or sends to (the written self-modification reading of the text as a skill's prose, every host a saved command contacts, and any network URL or mail address anywhere in the text, prose of a memory note included); `permission` a saved step that the self-modification, guardrail or privilege rules flag (permissions, tool allowlists, host or agent config, plugins, hooks, the scheduler, approvals, privilege), with every rule pack on, and never for the write into the memory or skill store itself; `secret` a redaction placeholder, a redactable shape or a secret-like value. Every line of a script file a save writes (by its path, or a `#!` line) is a command, and so is a line outside a recognised fence that starts like a command, which covers an edit fragment inside a fence it does not show, indented blocks and longer or unclosed fences. Other string arguments (a description) are read for destinations and secrets. A rule that fails, or a save with more commands or code spans than are read, counts as adding that kind. A recipient named without an address and a step written only in prose are left to the self-edit judge.
- The `command` reading for this field leaves out what is shown rather than run: fenced blocks tagged as text, log or output; log-shaped lines in a fence (a date or time, a bracketed tag, an upper-case level, a placeholder); output lines in a console transcript with `$ ` prompts; inline code that is a flag fragment, a setting, quoted text or plain prose; and, in a memory note, inline code the sentence only reports on (`` `npm ci` failed ``). When in doubt text is a command. The judged skill steps (`selfedit.risky_step`) keep their reading, and the permission rule still checks every candidate the wider reading finds.
- `lenient` (`converge.self_edit`) is true only when `adds` is empty or only `command`, the self-edit judge answered (its envelope OK with every answer present) and its `untrusted_directive`, `weakens_oversight` and `unsupported_owner_claim` answers are each below `LENIENT_ANSWER_LIMIT` (0.7, the raw probability), and no floor applies (enforced, guardrail, or score-only); the rule probe must have answered and no probe that sets floors may have failed, since convergence takes floors only from probes that answered. It says nothing about the verdict: a plugin that cannot ask anyone about a background save consults it only when the risk is in its review band.
- No score, reason, floor, relief, question or verdict changes: the field is computed after the probes and read by nothing else.
- Tests: `test_self_edit_save` (lenient: a plain memory note, a skill of ordinary git and test-runner steps with mild answers, a write into the skill folder under the host's agent directory, an OpenClaw day note, a memory save made by a plain shell append, answers at 0.69; not lenient: a skill step that changes a tool allowlist, approvals, the scheduler, plugins or privilege, the same change inside an edited fragment or a text fence, a placeholder and a secret-like value, a mail recipient or URL in a memory note's prose, an upload and a remote in a skill, a prose-only note with `untrusted_directive` 0.75, each answer at exactly 0.7, a non-finite or non-numeric answer, a failed judge, a missing answer, no self-edit questions, the input-size floor and any floor, a failed or skipped rule probe and a failed context or oracle probe, a script file, a `#!` script, an indented block, a four-backtick fence, an unclosed fence, an edited fragment, a mail address in a description; the field absent on an owner turn and without the block; `adds` sorted and de-duplicated; schema validation; the false positives above with the wider reading still counting them; more commands or code spans than are read; and the whole response otherwise identical with and without the field for seven self-edit requests under good and bad answers).
- Tightened before release (`lenient` only; `adds` gains readings, no score moves):
  - Not lenient when any rule fired on the saved content: a finding on a saved skill step (a credential read, a decode into a shell, a package install), or on the save itself beyond the write into the declared store. A memory note's steps, which the rule-based probe does not judge, are checked by the reading with every rule pack on.
  - The judge guard also covers `persists_secret` (below 0.7) and `concealment` (the probability of hidden intent, level 2, below 0.7). `grounded` stays out of the guard: on real background saves a limit would cost most of the rescued memory notes.
  - Not lenient unless the scan's status is ok, no probe failed or fell back, the entity lookup answered from a library, and the rule-based probe and the judge answered.
  - Not lenient when the save writes no content the reading examined (a restore, an archive, a support-file removal), removes content the request shows and writes nothing in its place (a remove, delete or archive action, a replaced text with a word the save does not write again and empty new text, a patch's removed lines likewise, a command that deletes, moves, truncates or edits in place), holds code the rules cannot read (a program in a variable, PowerShell or batch, more steps or longer steps than the rule-based probe reads), or writes outside the declared store (a path outside the store's folder group and the workspace, or a workspace path in an agent, credential or system group).
  - An edit that replaces text with new text and drops a word of it (a rewording) is lenient only while the judge's `weakens_oversight` answer is below `REWRITE_OVERSIGHT_LIMIT` (0.5); a missing answer is not lenient. An edit that writes every word it replaces again is not a rewording.
  - The reading also sees lines that start a subshell, a group, a command substitution or a variable, list items that read as code, and `<pre>` blocks; `chmod` to world-writable or setuid, ACL grants, attribute changes and `crontab` installs count as `permission`; `scp`, `rsync`, `sftp` and `rclone` remotes and a `git push` to a remote other than `origin` or `upstream` count as `destination`; a sign-in pair (`login is admin / <passphrase>`) counts as `secret`.
  - A URL in a saved text's prose that only points to reading matter ("see the docs at", "reference:", in a sentence with no send or run verb) is no longer a `destination`.
  - Fences are found in one pass over the lines, and the prose reading gets its code blanked out first: a 95,000-character skill of unclosed fences took 69 s in the reading, now 0.3 s.
  - The reading reads text as a reader takes it: compatibility forms folded (NFKC), invisible characters dropped, HTML entities decoded, defanged addresses (`hxxp`, `[:]`, `[.]`, `(dot)`) restored, and backslash-newline continuations joined.   - A rewording is read per edit: an edit's replaced text is compared with that edit's own new text, and any change to a sentence holding an oversight or negation word (never, always, ask, approve, confirm, not, without, before, permission, …) is a rewording even when no word is dropped.   - Saves made by running a command have their heredoc bodies read as saved text. A program word written quoted or escaped, and a shell function's body, are read as the shell reads them. A description, a reason field and a skill's front-matter description are read for commands named in prose.
  - A skill-tool save whose name or file path is absolute or climbs out with `..` is outside the store.
  - Cheap secret shapes: "password/passphrase/passcode is <word>" in any case, a PIN of digits, a Luhn-valid card number, a base32 seed after 2FA/OTP/TOTP, a recovery phrase after seed/recovery/mnemonic, and a vendor token written with spaces between its characters.

  - Program words are shell-unquoted (`her'mes'`, `her""mes`, `her\mes`, `$'hermes'`) and simple aliases resolved; heredoc delimiters may be any token.
  - Whole-file writes (`write`, `write_file`, `create`) are rewordings, and one of fewer than three words to an instruction file is a removal.   - More secret spellings: `pw`, "PIN code", "was changed to", "password - x", spaced card digits, base32 seeds in groups or lower case, numbered or line-split recovery phrases and "backup words".
  - The rule-based probe's findings on the save itself are reused instead of running the rules again, and the remaining unbounded patterns are bounded.

### A skill review reading its own skills is not a self-modification (2026-11-19)
- OpenClaw Code Mode cells: PlanIR `pending_call` gains an optional `input_kind`. The OpenClaw plugin sends `javascript` when OpenClaw marks the call on its hook event as a Code Mode cell (the `exec` that runs JavaScript and reaches files, commands and the network only through nested tool calls, each hooked and scanned on its own); never from the call's arguments. For such a cell on OpenClaw, the rule-based probe takes no written file from reading the JavaScript as shell (an arrow function `f => f.name` or a comparison `n > 0` was a "redirect" into the working directory); a write the cell's command strings spell out is still a destination. The field is left out of the judge's views, so their requests are unchanged. Only a tool named `exec` is marked (OpenClaw marks only its Code Mode tool). The credential-to-own-service relief checks a cell's own prints and writes as code, as it does for other inline code, so a cell that puts the key elsewhere is not relieved.
- A redirect whose target starts with a bare `(` or `)` names no file: a shell cannot run it (the parser met it only in JavaScript read as shell, such as `t => (t.name || t.id)`, also from hosts that send no mark). A quoted name that starts with a parenthesis still counts.
- `echo` and `printf` no longer count as writing the files their arguments name (`guardrail` list version 7): they print their arguments, and only a redirect, counted on its own, makes them write.
- Why: OpenClaw's Skill Workshop review can work in the agent's own skill folder, so these misreadings put a "write" into the agent's own directory, which scored as a self-modification at block level and stopped the review before it reached its save. These are parsing rules for every session: background runs get no relief of their own, and writes, reads outside the skill folder, `..` escapes from it and attended sessions score as before.
